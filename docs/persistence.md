# Persistence model

## Why the production database is still TBD
The bank has not decided the production integration database (Oracle is a possibility, not a decision). So:
- Application code depends only on `IKycCaseRepository` / `IReferenceMappingRepository` (domain-friendly methods, no ORM types).
- TypeORM is used **inside `src/persistence`** only; its `DataSource` and repositories are not exported from the module.
- SQLite (`better-sqlite3`) is supported **for local dev/test only**. `buildDataSourceOptions` throws `UnsupportedDatabaseError` for any other `DB_TYPE` and for SQLite when `NODE_ENV=production`. No Oracle credentials or connection settings exist.
- When the engine is chosen: add its driver, a `DB_TYPE` branch in `database.config.ts`, and a migration set for it. The first migration is SQLite-specific (`datetime`, `datetime('now')` defaults) and must not be edited for another engine.

## Schema management
- Migrations live in `src/persistence/migrations/`; `synchronize` is **always false** and `migrationsRun` is false. Tests run the real migrations on an in-memory database.
- Run: `npm run migration:run` (revert last: `npm run migration:revert`). Path from `DB_SQLITE_PATH` (default `./var/kyc-local.sqlite` outside production).
- A test checks entities and migrations agree (TypeORM schema builder reports no pending changes).

## Table `kyc_case`
| Column | Notes |
|---|---|
| `internal_id` PK | UUID generated by the app |
| `kyc_ref_no` | **unique**; FLEXCUBE KYC_REF_NO |
| `reis_system_id` | **unique**; value sent to REIS as `systemId` (= KYC_REF_NO today) |
| `customer_no` | nullable, indexed; attached once FLEXCUBE creates the customer |
| `reis_customer_id`, `risk_calculation_id`, `reis_id` | nullable REIS identifiers |
| `customer_type` | INDIVIDUAL / CORPORATE |
| `internal_request_status` | `KycRequestStatus` (internal lifecycle) |
| `reis_onboarding_status` | nullable: CLEAN / PENDING / REJECT |
| `final_status` | nullable: CUSTOMER / BLOCKED, set at most once |
| `final_status_at`, `final_status_received_count`, `conflicting_final_status` | webhook idempotency foundations |
| `retry_count`, `last_error_code`, `last_error_message` | retry/error state (message truncated to 1000 chars, code to 100) |
| `created_at`, `updated_at` | timestamps |

Not stored: tokens, passwords, REIS credentials, full request/response payloads. Callers must not put secrets in error messages.
Enums are stored as plain `varchar` (no DB enum types) to stay portable.

## Webhook idempotency foundation
`applyFinalStatus(systemId, status, reisCustomerId?)` is keyed by REIS systemId and never overwrites an existing final status:

| Situation | Outcome | State change |
|---|---|---|
| No case for systemId | `UNKNOWN_CASE` | none (caller logs it) |
| No final status yet | `APPLIED` | final status set once (conditional UPDATE), internal status `FINALIZED`, `reis_customer_id` stored if empty |
| Same final status again | `DUPLICATE` | only `final_status_received_count` increments |
| Different final status | `CONFLICT` | original kept; `conflicting_final_status` records the attempt |

The handler itself (`/customerStatus`) is Step 7. How REIS retries remains TBD; this design does not depend on it.

## Table `reference_mapping`
`id`, `mapping_type`, `flexcube_value`, `reis_value`, `description` (nullable), `active`, `created_at`, `updated_at`; unique on (`mapping_type`, `flexcube_value`).
- Lookup = exact, **case-sensitive**, **no trimming or case folding**, **only active rows**, and an in-code exact comparison so a case-insensitive DB collation cannot change behavior.
- Stored values must be non-empty and have no leading/trailing whitespace (rejected with `InvalidReferenceMappingError`).
- No match -> `UnmappedReferenceValueError` (never a pass-through).
- The table is **empty**: no Bank mappings are seeded. Corporate Account Purpose 203/204 and the DOCUMENT_TYPE list still need Bank verification.
- `SOURCE_OF_INCOME` stores per-value mappings only. The rule collapsing several ticked checkboxes into one REIS value is TBD and not implemented.

## Internal statuses added in Step 5
`DELIVERY_UNCERTAIN` (onboarding outcome unknown; sent again by the poller) joins `RECEIVED`, `VALIDATION_FAILED`, `SUBMITTED_TO_REIS`, `REIS_CLEAN`, `REIS_PENDING`, `REIS_REJECTED`, `FINALIZED`, `FAILED_RETRYABLE`, `FAILED_PERMANENT`. Statuses are plain `varchar` values, so no migration was needed. Repository methods: `recordValidationFailure`, `recordDeliveryUncertain`, `reopenForRetry` (conditional update, only from a retryable status: `RECEIVED`, `SUBMITTED_TO_REIS`, `VALIDATION_FAILED`, `FAILED_RETRYABLE`, `DELIVERY_UNCERTAIN`). See `docs/workflow.md`.

## Added in Step 6 (migrations 2 and 3)
- `kyc_case.reis_instruction`, `kyc_case.reis_error_message` (nullable, 4000 chars): REIS onboarding response text. Sensitive: stored, never logged.
- `kyc_case.flexcube_update_status` (default `NOT_ATTEMPTED`), `flexcube_update_error_code`, `flexcube_update_error_message`, `flexcube_updated_at`: the FLEXCUBE update, tracked separately from `final_status`.
- Table `webhook_event`: `/customerStatus` audit (see `docs/customer-status-webhook.md`), indexed by `system_id` and `kyc_case_internal_id`.
- `applyFinalStatus` now also returns `CUSTOMER_ID_MISMATCH` and `INCONSISTENT_STATE`, applies only to `REIS_PENDING` cases, and arms `flexcube_update_status = PENDING` in the same atomic update.
- New repositories: `IWebhookEventRepository` (`start`, `complete`, `findByEventId`, `listBySystemId`); `IKycCaseRepository.recordFlexcubeUpdateResult`.
- Transaction note: SQLite correctness relies on atomic conditional UPDATEs. This is not the final production transaction design; review it when the production database is chosen.

## Added in Step 7 (migration 4)
- `kyc_case.flexcube_update_attempt_count` (integer, default 0) and `flexcube_last_attempt_at`: every call of the FLEXCUBE updater is counted and stamped. Technical bookkeeping only.
- `DELIVERY_UNCERTAIN` cases that later receive a final callback are not changed: `applyFinalStatus` returns `RECONCILIATION_REQUIRED` and the audit row keeps the incoming status.
- `IWebhookEventRepository.listByKycCaseInternalId`, `listByResults`; `IDatabaseHealthCheck.ping` (ORM stays private to the persistence module).
