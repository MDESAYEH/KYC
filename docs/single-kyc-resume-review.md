# مراجعة استكمال تجربة العميل — 19 نوفمبر 2026

> هذه مراجعة مرحلة التصميم. متابعة التنفيذ المحلي ونتائج اختبارات Oracle الفعلية وخطة النشر والتراجع في [تقرير التنفيذ](kyc-resume-implementation.md). تبقى أرقام الاختبارات أدناه سجلًا للجولة السابقة.

الحالة: خطة للمراجعة مع بوابات تحقق واختبارات معزولة. لا يوجد أمر CLI للاستكمال أو adapter يكتب على Oracle ضمن هذا التعديل. لم يُنفذ إرسال، اتصال بـUAT1، reset، migration أو تغيير إعدادات. تبقى موافقة التنفيذ الصريحة مطلوبة لاحقًا؛ هذه الوثيقة ليست موافقة.

## نطاق الأدلة وحدود الاستنتاج

السجل المحدد: CIF `00005804`، KYC `001ZKYC26151003Y`، SEQ_NO المستهدف = `STTM_CUSTOMER.MOD_NO = 1`، وليس KYC MOD_NO الذي ظهر سابقًا بالقيمة 2. الحالة المبلغ عنها: trigger E، staging E، REQUEST/RESPONSE موجودان، REIS_FINAL_STATUS NULL.

| المحاولة | الدليل المتاح في هذه المراجعة | ما يمكن استنتاجه |
|---|---|---|
| الأولى | runbook المحلي يصف توقف 19/11 عند authenticate، مع timeout/base URL/firewall ومؤشر wire=null | وصف تاريخي يحتاج مطابقة مع ملفات المحاولة الفعلية وسجلات REIS؛ لا يثبت غياب المعالجة بمفرده |
| الثانية | إفادة المستخدم: authenticate HTTP 403 بسبب قراءة password بصورة ناقصة من .env، ثم نجاح اختبار مصادقة مستقل HTTP 200 | إذا رُبط خطأ authenticate بالمحاولة نفسها، فالتنفيذ التسلسلي لا يصل إلى Onboarding فيها. نجاح auth لاحقًا لا يثبت نجاح onboarding أو غياب طلب سابق |

حادثة ORA-01745 الأقدم موثقة في runbook أيضًا، لكنها ليست تلقائيًا إحدى محاولتي HTTP المذكورتين. يجب جرد المعرفات والأوقات وملفات الأدلة الفعلية لتحديد المحاولتين قبل الموافقة. لا نختلق معرفات أو timestamps ولا نعيد تصنيف السجلات التاريخية تلقائيًا. لم تتوفر هنا ملفات المحاولتين الأصلية أو سجل REIS؛ لم نقرأ بيانات العميل الحية.

## سبب التصنيف الحالي

`ReisOnboardingClient.onboard()` ينفذ authenticate أولًا ثم searchOnboardCustomer. `ReisAuthenticationError` يحتفظ بـoperation وHTTP status، والمصنف العام `classifyReisFailure` يميز authenticate بالفعل، لكنه لم يكن مستخدمًا في مسار التجربة المفردة.

`sendSingleKycTrial` كان يستخدم catch دون فحص الاستثناء: كل خطأ يؤدي إلى SINGLE_TRIAL_DELIVERY_UNCERTAIN، wire=null أو wire محفوظ، ثم staging E وtrigger E. عدم وجود wire.json يعني غياب استجابة Onboarding المحفوظة فقط، ولا يثبت أن Onboarding لم يُرسل. كذلك REQUEST هو intent يُحفظ قبل المصادقة، فلا يثبت وصول طلب إلى REIS.

التعديل المحلي يميز **الاستدعاءات المستقبلية**:

| الخطأ | تسجيل التجربة | السماح بالتكرار |
|---|---|---|
| خطأ typed من authenticate مع غياب onboarding wire | NOT_SENT، stage=REIS_AUTHENTICATE، code/HTTP status، requestMayHaveReachedReis=false؛ حالة محلية FAILED_PERMANENT أو FAILED_RETRYABLE وفق المصنف | ممنوع تلقائيًا في الحالتين |
| timeout/reset/5xx أو body غير صالح أثناء Onboarding | DELIVERY_UNCERTAIN | ممنوع؛ مصالحة مطلوبة |
| HTTP 401/403 من Onboarding نفسه | يبقى uncertain في مسار التجربة؛ الاستدعاء خرج فعلًا | ممنوع |
| خطأ مجهول أو أدلة متعارضة | uncertain حتى مع wire=null | ممنوع |

NOT_SENT هنا تعني أن **طلب Onboarding لهذه الدعوة** لم يُرسل؛ authenticate نفسه قد وصل إلى REIS. لا تعني أن العميل لم يكن لديه طلب من محاولة أخرى. FAILED_RETRYABLE تصنيف تقني وليس إذن إعادة إرسال.

## لماذا لا نستخدم أدوات الاسترجاع الحالية؟

- `restoreNeverSent` يفترض REQUEST وREQ_DATE فارغين، marker تقني ORA/NJS/DPI، trigger U ومراجعة CIF ثابتة. السجل المبلغ عنه لا يطابق هذه الشروط.
- `applyReset/resetUndelivered` مسار آخر يمسح REQUEST/RESPONSE والتواريخ ويصفر العداد، ثم يحذف local case. مرجع REIS نصي قصير وغياب wire وحدهما لا يحققان اشتراط إثبات المحاولتين وحفظ التاريخ. قد يفشل بين كتابة Oracle وحذف SQLite. **لا يُستخدم لهذا الاستكمال**، حتى لو وافقت صيغة marker القديمة شروطه.
- لا DELETE للحالة أو webhook_event، ولا تعديل revision_count للتحايل على حماية callback، ولا E→N أو E→U ليبدو السجل غير مجرب.

## خطة التنفيذ المقترحة

1. **حزمة مراجعة دون كتابة:** جرد المحاولتين بمعرفات وتوقيتات ومراحل HTTP؛ نسخ محمية كاملة من before/failure/wire، صف staging بجميع حقوله وتواريخه وMSGID، trigger، CIF MOD_NO، local case وجميع callback audit. تخزين hashes وبصمة payload الجديد ومصدر التحويل. الغياب أو التعارض يمنع التنفيذ. لا نغير الأدلة القديمة أو ننشر بياناتها في stdout.
2. **تأكيد REIS موثق:** وثيقة من مسؤول REIS، برقم مرجعي وهوية وتوقيت وhash، تنص صراحة على أن **كلتا المحاولتين لم تنشئا ولم تعالجا Onboarding**. تغطي CIF وKYC وهوية systemId القديمة إن استُخدمت، جميع correlation/request IDs والفترات الزمنية. لا يكفي token صالح أو غياب callback أو نفي معالجة إحدى المحاولتين فقط. يتحقق المراجع من أصالة الوثيقة خارج البرنامج؛ hash ليس توقيعًا أو إثبات هوية.
3. **خطة مثبتة وموافقة مستقلة:** ربط الموافقة ببصمات الأدلة والحالة والـpayload، MOD_NO=1 وSEQ_NO=1 وMSGID، ومؤشر callback audit، ونسخة الكود وSQL، وتوثيق تعطيل بقية المرسلين. يلزم أيضًا اعتماد مصدر CIF وقواعد CLEAN/PENDING/BLOCKED ومسار callback والنسخ الاحتياطية كما في موافقات التجربة الأصلية. لا تُستخدم موافقة المحاولة القديمة. بوابة المراجعة الحالية تفترض صلاحية ساعة لكل تأكيد وموافقة كاقتراح محافظ قابل للاعتماد لاحقًا، وليس قاعدة صادرة عن REIS.
4. **سجل محاولات دائم append-only:** إضافة attempt جديد، مرتبط بالمحاولتين لا بديل عنهما، مع سجل انتقالات STARTED/AUTH_FAILED/ONBOARDING_DISPATCH_INTENT/RESPONSE_CAPTURED/WRITEBACK_PENDING/COMPLETED أو UNCERTAIN. حفظ snapshot السابق قبل أي استبدال لحقول current staging، مع receipts لكل كتابة وسببها وهوية الموافق. لا تصفير RETRY_COUNT؛ زيادة المحاولات عند الحد المعتمد وتوثيقه. يبقى local case بنفس هويته وتُربط محاولة الاستكمال به؛ تُحفظ حالته السابقة كحدث مستقل بدل الحذف.
5. **حجز لمرة واحدة وفصل قواعد البيانات:** مفتاح فريد للنطاق CIF/KYC/SEQ مع attemptId وplan hash؛ تثبيت الحجز والأدلة في transaction واحدة محلية. CAS على Oracle للصف المحدد وحالته وبصمته ومراجعة CIF، مع قفل/حماية trigger E→P وفق SQL جديد معتمد للاستكمال، لا restoreNeverSent. SQLite وOracle لا يشكلان transaction واحدة: durable journal وخطوات قابلة للمصالحة مطلوبة. crash أو فقدان ACK بعد الحجز يحظر إعادة الاستدعاء مهما كانت مرحلة الخطأ؛ لا تحرير تلقائي للحجز أو انتهاء lease يتيح الإرسال مجددًا. فشل حفظ الأدلة قبل الحجز يمنع أي HTTP.
6. **فحص ثان قبل dispatch:** إعادة فحص STOP والموافقة وتوقف polling والمرسلين وMOD_NO والمصدر والـpayload والحجز وcallback watermark بعد authenticate وقبل Onboarding نفسه. العميل الحالي يفحص STOP قبل onboard الذي يتضمن auth؛ يحتاج adapter الاستكمال بوابة إضافية بينهما. تغير CIF أو وصول callback يلغي الخطة ويُدقق الحدث. الحجز يمنع عمالنا فقط، فلا يعوض تأكيد REIS أو إيقاف المرسلين الآخرين. يلزم اتفاق تجميد التعديل/قفل مراجعة CIF خلال نافذة dispatch؛ فحص قبل HTTP وحده لا يزيل السباق مع Oracle أو callback.
7. **نتيجة حقيقية ثم writeback فقط:** حفظ wire الحقيقي بصورة دائمة قبل parse، ثم تحديث الحالة المحلية وstaging إلى S من الاستجابة المعتمدة فقط. CLEAN→CLEAN، PENDING→PENDING وانتظار callback، REJECT→BLOCKED وفق mapping المعتمد. HTTP200 مع body غير صالح لا يسمح بـCLEAN. فشل التسجيل بعد HTTP يتحول إلى WRITEBACK_PENDING/UNCERTAIN مع حفظ الحجز؛ الاستكمال يكتب النتيجة المحفوظة فقط ولا يعيد Onboarding.
8. **قراءة تحقق:** exact KYC/SEQ/MSGID، PROCESS_STATUS=S، REIS_FINAL_STATUS مطابق للنتيجة الحقيقية، REQUEST/RESPONSE موجودان، وREADY_TO_SCAN=P حسب عقد Finexta الحالي. لا قيمة نجاح جديدة مفترضة للـtrigger؛ P تعني picked وليست قرار CLEAN. عند فشل المعالجة E مع توثيق النتيجة وعدم مسح الأدلة. إذا تغير MOD_NO بعد الإرسال لا نطبق قرارًا على النسخة الجديدة؛ نحفظ الاستجابة ونطلب مصالحة. فشل readback يمنع الإرسال الثاني.

## Callback بعد محاولات متعددة لنفس المراجعة

الـcallback يحمل systemId ولا يحمل attemptId أو SEQ_NO. الحماية الحالية المتعلقة بتعدد **المراجعات** لا تكفي عندما توجد محاولات متعددة على SEQ_NO نفسه. قبل الاستكمال، أي callback يوقف الخطة ويُحفظ للتسوية. بعد الاستكمال، يجب حجر callback غير القابل للربط بمحاولة محددة؛ لا ننسبه تلقائيًا للمحاولة الأخيرة لمجرد تطابق CIF. يلزم correlation موثوق من REIS أو تحقق تشغيلي موثق من مصدر القرار، مع مطابقة customerId إن كان معروفًا. إلى أن يعتمد ذلك، قد يبقى PENDING قيد المصالحة ولا يتحول إلى CLEAN.

يجب أن يشترك reservation وcallback handler في fence دائم لكل الهوية: تسجيل الحدث أولًا، ثم إبطال الخطة/تحديد قابلية الربط تحت القفل نفسه. التكرار المطابق يُدقق دون إعادة إرسال أو تغيير القرار؛ القرار المتعارض يُحجر. لا كتابة إلى MAX(SEQ_NO) أو مراجعة أحدث.

## المنفذ محليًا وحدود الاختبار

- تصحيح تشخيص authenticate في `single-kyc-trial.ts` مع حفظ code/stage/status دون credentials أو token أو auth response body؛ لا تعديل رجعي على السجل الحالي.
- إضافة readback لـREADY_TO_SCAN=P إلى تحقق نجاح التجربة.
- `single-kyc-resume.plan.ts`: بوابة offline ثابتة للسجل، تتطلب دليل محاولتين وتأكيد REIS الصريح وموافقة تنفيذ منفصلة وحالة لم تتغير. لا اتصال بقاعدة بيانات ولا إرسال ولا أمر apply.
- تجربة SQLite في الاختبارات فقط تثبت unique reservation وحفظ الأدلة وrollback عند فشل النسخ ومنع الحجز الثاني بعد توقف محاكى. ليست production adapter، ولا اختبار تعدد عمليات حقيقية أو recovery بعد إعادة تشغيل قاعدة file-backed.
- اختبارات HTTP تستخدم REIS وهميًا على loopback، وحالات محلية بSQLite memory، وOracle executor وهميًا. اختبارات callback الحالية تتحقق من exact revision والتكرار والتعارض والحجر؛ لا تثبت حل ربط callback بمحاولة الاستكمال الجديدة.
- لم يُنفذ SQL الاستكمال على Oracle؛ adapter وmigration وcallback fence وحقن الأعطال بين Oracle/SQLite والـdispatch تبقى بنود تنفيذ لاحقة قبل أي جاهزية حية. لا يصح اعتبار نجاح هذه الاختبارات إذن إرسال.

- تغطية الاستكمال: رفض غياب تأكيد REIS أو عدم شموله المحاولتين أو انتهاء صلاحيته، تغيير الأدلة والـpayload وMSGID، غياب الموافقة، تغير MOD_NO، وصول callback، تكرار الحجز، توقف محاكى بعد الحجز، وفشل حفظ الأدلة. تغطية التجربة تشمل auth 401/403 مقابل onboarding 403، timeout/5xx/body غير صالح، CLEAN/PENDING الحقيقيين، ورفض نتيجة stub المخالفة لـwire.

لا اتصال REIS حقيقي ولا UAT1 ضمن التحقق. لم يُعدل .env أو STOP؛ تطابقت بصمة .env قبل التحقق النهائي وبعده. لا تمكين polling أو نشر أو commit/push. لم يُفحص STOP على الخادم أو تُثبت حالته عن بعد لأن هذه المراجعة محلية دون اتصال تشغيلي.
